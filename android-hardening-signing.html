01加固是什么？为什么需要它？

Reinforcement / Packing / 加壳 —— 给 APK 穿上一层“防弹衣”

一句话定义：加固就是把 APK 里可以被轻易反编译成源码的 classes.dex 加密隐藏起来，替换成一个只有“解密 + 加载”功能的壳程序；App 每次启动时由壳在内存里解密出真实代码再运行。整个过程用户无感知，但破解者拿到的是一份“读不出代码”的 APK。

为什么必须做这件事？看下面这条“不加防护时的破解链条”：

关键认知：Java/Kotlin 编译出的 .dex 与 Python 字节码类似，格式完全公开、可 100% 还原回近似源码。所以“发布 Release 版”并不等于保密，必须靠加固把 dex 藏起来。

02加固前后的 APK 结构对比

一眼看懂“壳”到底做了什么

“壳”（Shell / Stub）这个词的由来：就像给鸡蛋套一层壳——外部只能看到壳，里面的“蛋黄”（真实代码）被保护起来，只有程序自己（在运行时）能打开。

03加固的分类：从一代到三代

按“藏代码的方式和深度”划分，越往下对抗强度越高、性能损耗也越大

一代整体 DEX 加密（数字壳）

把整个 classes.dex 加密存放，启动时整体解密后加载。360 加固、腾讯乐固的基础方案。实现简单、兼容性好，但内存里能整体 dump 出明文 dex，脱壳工具（如 FRIDA-DEXDump）较易对付。

二代方法抽取 / 函数抽取

不加密整个 dex，而是把每个方法的指令体（方法体）抽走，只留空壳结构；方法被调用时才在内存中逐个还原。dump 出的 dex 缺方法体，需“主动调用”才能补全，对抗性明显提升。

三代VMP / Java2C（dex2c）

指令虚拟化：把 Java 字节码翻译成自定义虚拟机指令（VMP），或直接把关键方法转成 C 代码编译进 so（dex2c / Native 化）。即使脱壳也拿不回原始逻辑，是目前最强路线，但对性能、稳定性影响最大。

SO 加固 & 资源加固

对 lib/*.so（native 库）做混淆加壳：OLLVM 指令混淆、控制流平坦化、字符串加密、so 壳；对 res/ 资源加密防止资源被替换/盗图。与 dex 加固互补。

辅助防护层（通常与加固捆绑提供）

反调试

ptrace 自附加、检测调试器 / IDA / gdb，检测到就闪退。

反 Hook

检测 Xposed / Frida / Substrate 注入痕迹。

环境检测

模拟器、Root、多开、虚拟机框架识别。

完整性校验

运行时校验自身签名与文件哈希，防二次打包。

选型直觉：银行 / 证券类 App 常用“二代抽取 + so 加固 + 完整性校验”；游戏常用“so（OLLVM）加固为主”；普通 App 用一代整体加固已能挡住 90% 的脚本小子。

以上传到加固平台为起点，八步流水线

注意第 ⑦ 步：加固改动了 APK 内容，原有签名必然失效（签名本质上是对文件内容的哈希承诺）。所以“加固”和“重新签名”永远是一对搭档，详见第 11 节。

05运行时“脱壳”：App 启动后发生了什么

为什么用户感觉不到任何异常？——壳利用了 Application 初始化最早的时机

攻防就在第 ⑤ 步：一代壳的明文 dex 终究会完整出现在内存里，所以脱壳工具普遍采用“内存搜索 dex 魔数（dex\n035）+ dump”的思路。这正是二代“方法抽取”、三代“VMP/dex2c”出现的原因——让内存里永远凑不齐一份完整的明文 dex。

06什么是签名？—— 先懂“数字签名”再谈 V1/V2

签名回答两个问题：这个 APK 是谁发布的？内容被动过手脚吗？

两大基石：哈希 + 非对称加密

哈希（摘要）：把任意大的文件压成一个固定长度的“指纹”（如 SHA-256 输出 256 位）。改一个字节，指纹就面目全非 → 用于验完整性。
非对称加密：私钥 + 公钥一对。私钥签名（加密摘要），公钥验证（解出摘要）→ 用于验身份。私钥永远在开发者手里，公钥随证书公开。

签名的三大作用：①防篡改——改一个字节验证就失败；②防冒充——没有你的私钥就伪造不出你的签名；③防覆盖安装——Android 规定签名不一致的包禁止覆盖升级，防止别人用“升级”名义替换你的 App。

开发者的私钥保存在 key.jks（keystore）文件里，一旦丢失，App 将无法以原身份更新，只能换包名重新上架 —— 所以私钥要像命一样保管。

07V1 签名（APK Signature Scheme v1 / JAR 签名）

来自 Java 世界的老方案：在 META-INF 里放三份“清单”

# V1 时代的命令（JDK 自带，只能签 V1）
jarsigner -keystore key.jks app.apk myalias
# 校验
jarsigner -verify -verbose app.apk
一句话记住 V1：“给 ZIP 里的每个文件开收据，但不管 ZIP 这个包裹本身有没有被拆过。”

08V2 签名（APK Signature Scheme v2）

Android 7.0 (API 24) 引入：对整个 APK 一口气签名

V2 相比 V1 的质变

① 覆盖整个 APK——ZIP 结构也被保护，堵死“塞私货”类漏洞（Janus 无效）；② 校验更快——顺序读一遍文件即可，无需逐条解压；③ 安装期、运行期均校验。

兼容性策略

V2 需 Android ≥ 7.0 才认；低版本设备会直接无视 v2 块、退回校验 V1。所以面向老设备的包通常 V1 + V2 双签，两者都在、各取所需。

# 现代签名命令（build-tools 的 apksigner，默认 V1+V2+V3 智能齐签）
zipalign -v -p 4 app-unsigned.apk app-aligned.apk   # 先对齐！
apksigner sign --ks key.jks --out app-signed.apk app-aligned.apk
# 查看一个 APK 用了哪些签名方案
apksigner verify --print-certs -v app-signed.apk
# Verifies: v1: true, v2: true, v3: true ...
顺序很关键：使用 V2 时必须先 zipalign 再签名（对齐会移动字节、破坏 v2 签名）；老的 jarsigner 时代则是先签再对齐。用 apksigner 就按“align → sign”走。
一句话记住 V2：“V1 给每个文件开收据，V2 直接给整个包裹拍照存档——封条一动就报废。”

10360 加固全景剖析

把前面所有概念串起来：一个真实的商业加固产品长什么样

360 加固是什么

奇虎 360 推出的免费商用加固服务（360加固保 / reinforce），属于一代“整体 DEX 加密”壳的代表，兼具二代抽取能力，是国内市占率最高的方案之一。开发者把 APK 上传到其平台或用本地命令行工具处理，得到加固后的包，重新签名后即可分发。

特征指纹 —— 怎么一眼认出“360 加固的包”

反编译/解压一个 360 加固的 APK，你会看到：
├─ AndroidManifest.xml
│    android:name="com.stub.StubApp"          # 入口被换成壳的 Application
├─ classes.dex                        # 体积很小 = 壳代码（stub）
├─ assets/
│    加密的数据文件（原始 dex 密文，无法用 jadx 阅读）
├─ lib/{armeabi-v7a,arm64-v8a,x86}/
│    libjiagu.so / libjiagu_art.so / libjiagu_x86.so  # native 壳引擎
└─ META-INF/                          # 重新签名后的证书
识别套路通用化：任何商业壳都有“入口类替换 + 特征 so + 加密数据文件”三件套。看到 libjiagu*.so = 360；看到 libsecexe.so（梆梆）、libexecmain.so（爱加密）、腾讯乐固/网易易盾各自的 so，同理可辨。

11加固 × 签名：必须一起理解的两个概念

这是最容易踩坑、面试最爱问的结合点

三个高频踩坑点：
① 签名指纹变了——加固时用了不同 keystore，老用户将无法覆盖升级（Android 强制要求升级包与已装包签名一致）。始终用同一把 keystore 给加固包签名。
② 忘记重签——加固导出的包如果未签名/只签了 V1，在 Android 11+ 或部分市场直接装不上。用 apksigner 走完整流程。
③ 加固 ≠ 绝对安全——一代壳可被 dump，加固提高的是破解成本，核心密钥逻辑仍建议结合 so 加固 / VMP / 服务端校验。
开发者自校验（签名检查）：很多 App 还会在运行时（Java 或 native 层）读取自身签名的 MD5/SHA 并与硬编码值比对，不一致就退出 —— 这是防“二次打包”的常见配套手段，属于加固之外代码层的一层保险。

✓一页总结

概念一句话
加固加密 APK 里的 dex，换成“壳 + 密文 + native 解密引擎”，运行时内存中解密加载，防反编译破解
加固分类一代整体加密 → 二代方法抽取 → 三代 VMP/dex2c；配套 so 加固、资源加固、反调试等
签名哈希（完整性）+ 非对称私钥/公钥（身份），防篡改、防冒充、防覆盖安装
V1META-INF 三件套，逐文件校验；不保护 ZIP 结构，有攻击盲区
V2Android 7.0+，Signing Block 对整个 APK 签名，更快更严；现代标配（配合 V3/V4）
360 加固商业加固代表：dex 加密 + libjiagu*.so 引擎 + com.stub.StubApp 入口 + 平台重签名
二者关系加固改动内容 → 原签名失效 → 必须用原 keystore 重新签名才能安装升级
