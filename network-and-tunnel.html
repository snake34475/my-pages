01

从一个具体问题开始

一台电脑开了 VPN，交换机下的其他设备能进公司内网吗

先说结论：不能。开 VPN 的是那一台电脑自己，不是整个局域网。隧道是端到端的——一头在你电脑的虚拟网卡上，一头在公司网关。链路上的交换机和路由器只是搬运工，它们根本不知道有隧道存在。

这个问题看着小，但它牵出了后面所有的知识：隧道是什么、路由表怎么工作、设备之间怎么互相看见、什么设备能干什么。所以先把场景和结论钉死，再逐层拆。

1.1　场景与拓扑

路由器 LAN 口接一台二层交换机，交换机下面挂三台电脑。其中只有电脑 A 开了公司 VPN 客户端。

1.2　隧道为什么只属于一台设备

把它想成一条私人电话线：某台电脑和公司网关之间单独拉了一根线，线里的包裹被套了个壳（加密），外面的人只看得到壳。

关键在于这根线只有两个接口：一个在你的电脑上（一块虚拟网卡），一个在公司的 VPN 网关上。它天然是一对一的，不可能「一个房间的人都接进去」。

交换机全程不参与

二层交换机只认 MAC 地址，做的是「这个帧该从哪个口送出去」。它看不懂 IP，更看不懂隧道。而加密封装是电脑 A 上的 VPN 客户端软件自己完成的——套完壳之后，它就是交给路由器一个「看起来平平无奇的加密包裹」，跟平时刷网页没有任何区别。链路上没有一台设备知道「这里有条隧道」，自然也无从蹭进去。

1.3　拆分隧道与全隧道

这两个模式的区别，只影响同一台电脑自己的流量怎么走，不会让隧道扩大到整个局域网。它们改的都是电脑 A 的路由表，只是改法不同。

1.4　其他设备什么条件下才可能「借道」

所谓的「借道」，是让 B 把包交给 A，A 再替它从隧道送出去。这不是默认行为，必须三件事同时做到：

  1. B 得知道要走 A：手动把 B 的默认网关改成 A 的地址，或者加一条静态路由指向 A。
  2. A 得愿意帮别人转发：开启 IP 转发。Windows 上就是「网络共享（ICS）」，或者改注册表的 IPEnableRouter。
  3. A 得会改写来源地址：公司 VPN 网关只认隧道这头（电脑 A）的地址，B 的地址公司不认。所以 A 必须做 NAT（地址转换），并在防火墙上放行。

1.5　电脑上开 VPN vs 路由器上开 VPN

这两个差别巨大，很多人就是在这里搞混的。原因只有一句话：隧道的入口在哪台设备上，就只有那台设备（及其下游）进得去。

1.6　安全提醒：能访问这台电脑 ≠ 能进公司内网

同一台交换机下、同一个网段里的设备，本来就能互相看见——能 ping 通、能扫到开放的端口、如果开了共享还能进共享目录。这是局域网自身的性质，跟你开不开 VPN 一点关系都没有。如果你在电脑 A 上开了「文件共享 / 远程桌面」，哪怕不开 VPN 也是一样能被访问的。

但一定要把两件事分开：

两个完全不同的层次

能访问这台 VPN 电脑 = 邻居能串门（局域网自身的二层可达性）
能进公司内网 = 要拿到公司大门的钥匙（钥匙在那条隧道的另一头，不在局域网上）

真正值得警惕的风险是反过来的：这台电脑变成了「一把双门钥匙」——既暴露在同网段里被别人扫得到，又持有进公司内网的合法身份。一旦它被攻陷（弱口令、共享目录暴露、系统漏洞、装了带毒软件），攻击者就能拿它当跳板钻到公司内网里去。这在安全上叫 横向移动（lateral movement），也正是很多公司 VPN 客户端刻意默认禁止转发的原因。

几条实操建议
  • 不用公司 VPN 时及时断开
  • 这台机器别开面向同网段的共享目录、远程桌面
  • VPN 账号个人专用，别把电脑借给别人挂着你的 VPN 用
  • 真要「全屋都进公司内网」，正确做法是让 IT 在路由器或防火墙上配 VPN，而不是靠某台电脑当跳板
这一章的收口

VPN 隧道的入口在哪台设备上，就只有哪台设备进得去。隧道是「单人通道」，不是「整层楼的走廊」。

02

隧道是怎么套出来的

分层封装 · 两次查路由表 · 全隧道「反向的坑」

一句话结论：隧道不是「一条线」，而是把一个完整的 IP 包当成货物，塞进另一个包里运出去。原始包的源和目的地址一个字节都没变，只是外面又套了一层新地址。所以「谁在隧道里」由发起封装的那台设备决定，链路上的交换机、路由器只看到外壳。

1.1　按工作层次拆解各层职责

数据从你的程序发出去，要经过一条完整的栈。每一层只做一件事、只关心一件事。关键在于：隧道是在「网络层」和「链路层」之间硬插进去的一层，它把上面已经组装好的包整个当作载荷。

层次职责在这个场景里的具体表现
应用层产生数据、定义协议浏览器要访问 10.10.1.5:443
传输层分段、编号、重传、流控TCP 三次握手，端到端（你的电脑 ↔ 公司服务器）
网络层寻址 + 选路原始 IP 头：192.168.1.10 → 10.10.1.5
隧道层封装 + 加密整个包当载荷，加外层 IP 头（你的公网 IP → 公司网关）
链路层实际投递新包走物理网卡 → 交换机 → 路由器

1.2　完整链路：一次隧道内的访问

  1. 浏览器发起请求 → 传输层切成 TCP 段 → 网络层加上原始 IP 头：源 192.168.1.10，目的 10.10.1.5。

  2. 第一次查路由表。系统拿目的地址 10.10.1.5 去表里找，命中 10.10.0.0/16 → 隧道虚拟网卡。于是这个包被交给隧道网卡。

  3. 隧道网卡把整个包（含原始 IP 头）当作载荷，加密，再套一个新的 IP 头：源是你的公网地址，目的是公司 VPN 网关的公网地址。这一步多出来的协议头叫「隧道封装头」（IPsec ESP / WireGuard UDP / OpenVPN 等）。

  4. 第二次查路由表。这次查的是外层包，目的地是公司网关的公网 IP，命中 0.0.0.0/0 → 真实网卡。

  5. 从物理网卡发出 → 二层交换机（只按 MAC 转发，完全不知道这是隧道）→ 家用路由器做 NAT → 公网。

  6. 到达公司 VPN 网关：校验完整性 → 解密 → 剥掉外层头，得到最初那个原始包。

  7. 公司内网的路由器把原始包按 192.168.1.10 → 10.10.1.5 送进内网，到达目标服务器。

  8. 回包沿路反向走一遍：公司网关再套一次外层头 → 公网 → 你家路由器 → 你的电脑解密还原。

为什么交换机、路由器全程「看不见」隧道

它们看到的只是一个普通的、加密的、从你电脑发往某个公网 IP 的 IP 包。加密封装是在你的电脑上完成的，壳的里面是什么，链路上谁也看不到。这就是「隧道只属于一台设备」的物理原因——它是端到端的，中间设备只是一个搬运工。

1.3　全隧道模式的「反向的坑」

先说什么是「反向」：全隧道（Full Tunnel）本意是让你的所有流量都去公司，是个「管得更宽」的设置。但它的副作用是——连你家局域网里的其他设备，也访问不到你这台电脑了。方向反过来了，所以叫「反向的坑」。

原因是企业级 VPN 客户端除了改路由表，往往还会额外做两件事：

  • Kill Switch（断网保护）：通过 WFP / NDIS 过滤器驱动拦截流量，只要隧道没建立或掉线，就禁止任何包出去，防止数据泄漏。
  • 禁止访问本地网络（Block Local LAN）：明确拦截去往 192.168.x.x、10.x.x.x 等私有网段的流量。

当同网段的电脑 B 访问 A 的 192.168.1.10 时：

环节是否顺利说明
B 发出请求帧正常同网段，交换机二层直达
帧到达 A 的网卡正常物理层面完全没问题
A 的系统回应被拦过滤器驱动判定「这是本地网络流量」，直接丢弃
B 收到响应超时表现就是「ping 不通、连不上」
快速验证方法

把公司 VPN 从「全隧道」切成「拆分隧道」。如果 B 立刻就能访问 A 了，那就百分之百是客户端策略拦的，跟交换机、路由器、IP 配置都无关。

两套隧道打架：为什么关掉公司 VPN 再开 Clash TUN 会出问题

四层资源同时被争夺 · 不只是路由表被覆盖

一句话结论：不是「路由表被覆盖」这么单一。公司 VPN 和 Clash TUN 都是「全局接管型」工具，它们会同时争抢四层资源——虚拟网卡、路由表、DNS、过滤驱动。路由表只是其中最显性、最容易观察到的那一层症状。

2.1　被争夺的四层资源

层级公司 VPN 想要Clash TUN 想要典型后果
虚拟网卡自己的 TUN 网卡 + 固定接口索引新建 wintun 网卡并抢绑定顺序出现两个 TUN 网卡，绑定顺序错乱
路由表0.0.0.0/0 → 公司隧道0.0.0.0/0 → Clash TUN后启动者抢走默认路由，先启动的隧道断掉
DNS指向公司内网 DNS、加搜索域劫持到 fake-ip（198.18.0.0/16）内网域名如 git.corp.com 解析失败
过滤驱动Kill switch 拦截非隧道流量同样是 WFP 过滤器拦截并重定向包被丢弃或绕成环，行为不可预测

2.2　为什么「先关公司 VPN，再开 Clash TUN」这个顺序特别容易出事

正常退出时，VPN 客户端会做一套清理动作：删掉自己的虚拟网卡、删掉自己加的路由、把 DNS 改回去。但如果它是非正常退出（进程被强杀、驱动挂起、客户端崩溃、直接关机），这套清理就做不完，系统进入一种「半残留」状态：

  • 虚拟网卡还在，但已经没有任何程序在管它
  • 它加的 /32 路由和网段路由还留在表里
  • DNS 还指着公司内网服务器（这时候已经解析不了任何东西）
  • 过滤器驱动还挂在网卡上，规则却已经失效

这时候启动 Clash TUN，它会重新接管整个网络栈：创建新网卡、重写默认路由、劫持 DNS、注册自己的过滤器。问题在于——它不是在一个干净的环境里接管，而是在一堆残留之上接管。于是残留和新配置混在一起，形成一个谁都认不出的状态。

等下次再启动公司 VPN 时，它读到的系统状态和它上次退出时记事本上记的完全不一样，于是可能出现：反复重连、认不出自己的隧道、或者显示已连接但路由根本没生效。

更底层的原因：这三个东西都不允许「共享」
  • 命名资源独占：TUN 设备在操作系统里是具名对象，同一时刻只应有一个接管者。
  • 过滤器分层注册：WFP 过滤器按层注册，两个过滤器同时拦同一批包时，优先级和调用顺序由系统决定，结果不可预测。
  • 状态机假设：VPN 客户端内部维护着「我已连接 / 隧道 IP 是多少 / 我改过哪些路由」的快照，它假设自己是唯一的管理者。另一个工具动了系统状态，这个假设就不成立了。

2.3　症状对照表

你看到的现象大概率是哪一层出问题怎么确认
公司 VPN 显示已连接，但访问不了内网路由表——默认路由被抢route print 看 0.0.0.0 那行指向谁
内网域名解析失败，IP 直连却可以DNS——被 fake-ip 劫持nslookup 内网域名，看返回的 IP 是不是 198.18.x.x

2.4　想让两者共存，按这个来

  1. 最省事的办法：别同时开两个全局接管型工具。需要公司内网时用公司 VPN，需要出网时切 Clash，不并行。
  2. 必须共存时，把优先级定清楚：
    • Clash TUN 配置里排除公司 VPN 的虚拟网卡（interface-name 或 exclude-interface）
    • Clash 规则里给公司网段、公司 VPN 服务器地址加 DIRECT 规则，明确不走 Clash
  3. 启动顺序：先连公司 VPN，确认内网能通 → 再开 Clash → 开完用 route print 复查默认路由和公司网段的走向对不对。
  4. 出问题时的快速修复：全部退出（含托盘和后台服务）→ ipconfig /flushdns → 禁用再启用网络适配器，或者干脆重启系统。
  5. 最根本的解法：让公司 VPN 用拆分隧道模式，不去抢默认路由，冲突面立刻缩小一大半。
04

隧道的死循环：为什么必须给自己留一条 /32

外层包也要出口 · 先有鸡还是先有蛋

一句话结论：隧道的外层包同样需要一条出口路由。如果这条路由也没人管、被默认路由吞掉指回了隧道，那就形成一个「要发它就得先建隧道，要建隧道就得先发它」的循环依赖，隧道永远建不起来。

3.1　场景设定

  • 你的电脑：192.168.1.10，网关 192.168.1.1
  • 公司 VPN 网关的公网地址：203.0.113.1
  • 隧道虚拟网卡分配到的地址：10.10.0.200

全隧道模式下，客户端会往路由表里塞这些行：

10.10.0.0/16    →  10.10.0.200    （隧道网卡，公司内网走这里）
203.0.113.1/32  →  192.168.1.1    （★ 例外：去 VPN 服务器走真实网关）
0.0.0.0/0       →  10.10.0.200    （默认路由，全部改走隧道）

关键是带 ★ 的那一行。它的前缀长度是 32，比 0 长得多，所以在「最长前缀优先」的规则下，任何去往 203.0.113.1 的包都必定走真实网卡，绝不会落进默认路由。

3.2　如果没有那一行：完整死循环

3.3　为什么商业客户端很少踩这个坑

因为正规的 VPN 客户端在内部有一套严格的时序，它们是先留后路，再修大路：

  1. 读取配置，拿到服务器地址（这时候还不改任何东西）。

  2. 先在路由表里插一条 服务器IP/32 → 当前默认网关，并且把当前整张路由表和 DNS 设置存成快照。

  3. 开始握手、建隧道。因为有了第 2 步那条例外路由，握手包必定走真实网卡出去。

  4. 隧道建立成功，再把 0.0.0.0/0 改指向隧道网卡。

  5. 断开连接时，按第 2 步的快照把路由表和 DNS 原样恢复。

容易出问题的场景是手工配置：手写 WireGuard 的 AllowedIPs = 0.0.0.0/0、手写 OpenVPN 的 route 指令时，很容易漏掉「给服务器地址留一条例外」这一步。

WireGuard 的一个隐藏坑

如果 Endpoint 写的是域名而不是 IP，那么解析这个域名也需要走网络。如果那一刻 DNS 已经被指到了隧道内部的服务器，就会出现「为了连隧道，得先解析域名；为了解析域名，得先连上隧道」的二次死循环。所以 WireGuard 配置里 Endpoint 最好直接写 IP。

3.4　为什么 route print 里那么多 /32

你在 Windows 上敲 route print，经常看到一大串 xxx.xxx.xxx.xxx/32 的行。它们就是各路人马给自己留的「后门」——VPN 客户端、虚拟化软件、Docker、Clash 的 TUN 等等，都在用「加一条最具体的路由」这个手段，保证自己的关键流量不会被默认路由吞掉。

一句话记忆

默认路由是「其他都归我」。谁不想被吞掉，就给自己加一条更具体的 /32。前缀越长，说话越算数。

05

本机服务与防火墙方向

别人来连你，走的是入站 · 三个条件缺一不可

一句话结论：在 A 上起一个服务，同网段的 B 能不能访问，看的是 A 的入站（Inbound）规则，不是出站。方向搞反了，怎么调都没用。

5.1　入站和出站是两个方向

方向谁主动管什么Windows 默认策略
入站 Inbound外面的人连你别人的请求能不能进到你的服务阻止（除非有放行规则）
出站 Outbound你连别人你这台机器能不能出去访问允许
为什么响应包不用单独放行

Windows 防火墙是有状态的（stateful）：只要一条连接是你这边先发起的或者是被放行进来的，它回程的包会自动放行，不需要额外规则。所以「出站」基本不用动。

5.2　三个条件，缺一不可

Python -m http.server0.0.0.0（本身就是）不用改，直接就能被访问

127.0.0.1 是「本机回环地址」，只对本机开放。程序监听它，意味着「只有我自己能连」，别人发到 192.168.1.10:8080 的包根本没人接。

5.3　同网段通信压根不经过路由器

B 和 A 都在 192.168.1.x 里，B 做的事是发一个 ARP 广播问「A 的 MAC 是多少」，拿到之后直接把帧交给交换机，交换机再送到 A。整个过程中路由器完全没有参与。

所以在这个场景下，路由器怎么配都无所谓。只有 B 和 A 不在同一网段时，才需要路由器转发——那就还得额外确认路由器的路由和防火墙策略。

5.4　全隧道模式会从反面影响它

如果 A 开的是全隧道模式，而且客户端带了「禁止访问本地网络 / Kill Switch」这类策略，B 就算三条件都满足也连不上——包能到 A 的网卡（二层没问题），但 A 的系统不回应，因为流量被客户端自己的过滤器拦掉了。

快速验证：把公司 VPN 切成拆分隧道。如果 B 立刻能访问，就是这个原因。详细机制见第 2 章 2.1 与第 3 章 3.2。

一句话结论：VPN 和 Clash 长得像，但根本不是一个层次的东西。VPN 在网络层用虚拟网卡 + 路由表接管所有程序；Clash 在应用层开一个本地端口，只有主动把请求交过来的程序才走代理。

  • 规则模式 / 分流规则 ≈ 拆分隧道：DOMAIN-SUFFIX,google.com,PROXY 走代理，其余 DIRECT 直连。

IP 从哪来：交换机的边界在哪里

DHCP 的四个包 · APIPA 的自我救赎 · 为什么必须要有路由器

一句话结论：交换机不分配 IP，它连「IP 是什么」都不关心——它只认 MAC 地址。IP 是 DHCP 服务器发的；如果没人应答，设备会自己编一个（APIPA）。所以「没有路由器也能组内网，但一定上不了外网」。

4.1　交换机不做的事

功能二层交换机路由器
同网段内转发✅ 靠 MAC 地址表也能做，但没必要
跨网段转发❌ 看不懂 IP✅ 靠 IP 和路由表
分配 IP（DHCP）❌✅ 通常内置
NAT（私有转公网）❌✅
解析域名（DNS 代理）❌✅ 通常内置
隔离广播域❌ 反而扩散广播✅ 默认隔离
防火墙 / 流量控制❌✅

4.2　设备拿到 IP 的三条路

  1. 手工静态配置：自己填 IP、掩码、网关、DNS。好处是稳定可预测，坏处是要人工维护。
  2. DHCP 自动获取：向网络喊一嗓子，服务器分配给你。
  3. APIPA 自动配置：喊了没人应，自己挑一个用。

DHCP 的完整过程（DORA 四步）

  1. Discover（发现）：设备刚开机，还没有 IP，所以只能用源地址 0.0.0.0、目的地址 255.255.255.255 发广播：「这屋里有没有 DHCP 服务器？」

  2. Offer（提供）：DHCP 服务器收到后回应：「我可以把 192.168.1.20 给你用，租期 24 小时。」

  3. Request（请求）：设备再广播一次：「各位服务器注意，我要 192.168.1.20 了。」（这一步用广播而不是单播，是为了让所有 DHCP 服务器都知道它选了谁，从而收回其他家的 Offer。）

  4. Ack（确认）：服务器回一句「确认，拿去用」，同时把掩码、网关、DNS 一起给你。设备配置完成。

为什么全程靠广播

因为设备此刻还没有 IP 地址，无法进行任何单播通信。广播是「还不知道跟谁说」时唯一的通信方式。这也是为什么 DHCP 只能在同一个广播域里工作——广播穿不过路由器。

4.3　没有路由器、只有交换机、三台设备都设为「自动获取」会怎样

APIPA：喊不到人，就自己编一个

Windows 上看到 169.254.x.x 这种地址，就是「我没要到 IP」的信号。这个机制叫 APIPA（自动专用 IP 寻址），过程是：

  1. 从 169.254.0.0/16 这个专用网段里，随机挑一个地址
  2. 发 ARP 探测（ARP Probe）问：「这个地址有人用吗？」
  3. 有人回应 → 说明撞车了，换一个，回到第 1 步
  4. 没人回应 → 用这个地址，再发一次 ARP 通告声明占用
APIPA 的特点具体表现
地址范围169.254.0.0/16（168.254 段专用）
子网掩码固定 255.255.0.0，所以同网段范围极大
网关没有——所以出不了门
DNS没有——所以解析不了域名
能否互访能。三台设备都在 169.254.x.x，同网段，交换机直达

4.4　会不会 IP 冲突

  • APIPA 不会冲突：因为有 ARP 探测 + 通告这套机制，同一个广播域内每个人都能确认自己的地址没被占用。
  • DHCP 也不会冲突：服务器维护「已分配列表」和租约时间，不会重复发放。
  • 手工配置会冲突：如果两个人手动填了同一个 IP，操作系统在启动时会通过 ARP 检测到冲突，弹出「检测到 IP 地址冲突」的警告，然后那台设备可能干脆不启用网络。
  • 跨广播域的 APIPA 可能重复：两个互不相通的局域网各自用 169.254.1.1 是可能的——但它们本来也通信不了，所以无所谓。

4.5　那为什么还需要路由器

因为「组内网」和「连外网」是两件事。路由器解决的正是交换机做不到的那部分：

  1. 跨网段转发：交换机只能在同一个网段内转发（靠 MAC）。一旦目标在别的网段，交换机不知道该怎么办。路由器负责「从这个网络送到另一个网络」。
  2. NAT：内网用的 192.168.x.x / 10.x.x.x / 172.16~31.x.x 是私有地址，在公网上根本不存在、也不允许出现。必须由路由器把它们翻译成一个真实的公网地址。
  3. DHCP + DNS 代理：自动分配地址、告诉设备去哪解析域名。
  4. 隔离广播：广播不会穿过路由器。这样每个网段内的广播量才可控。
  5. 防火墙与流量控制：能拦、能限速、能记录。

4.6　路由器与交换机的关系

一个比喻

交换机 = 一栋楼里的内部邮差：他认识楼里每个人的房间号（MAC 地址），只负责楼内投递，不知道楼外还有世界。
路由器 = 连接不同楼栋的跨城快递：他认识城市和街道（IP 网段），负责把包裹从一个网络送到另一个网络。

层级关系上：路由器在上，交换机在下。路由器的一个 LAN 口接一台交换机，就构成一个「子网」；多个子网用路由器连起来，才成了互联网的雏形。

一个重要的事实：你家的「路由器」其实是五个东西合体

路由器 + 交换机 + 无线 AP + DHCP 服务器 + 防火墙/NAT。所以它才能一根网线进来、几台设备出去、还自动分地址。拆开看，每一部分都不是必须绑在一起的。

设备的能力边界

什么结构能借道 · 谁能开 VPN · 没有路由器能不能上网

一句话结论：判断「能不能」的时候，别盯着拓扑长什么样，只看两条：二层能不能互通、IP 是不是同一网段。中间挂的是路由器、交换机还是光猫，不影响同网段设备之间互相看见。

8.1　借道的判据只有两条

网络结构二层能互通同网段能否借道
光猫 / 路由器下，设备都在 LAN 侧能是能
路由器 + 交换机，都在 LAN 侧同一网段能是能
只有交换机，网关在上一级，同一网段能是能
设备接在路由器 WAN 侧，或分属不同网段不能否不能
路由器开了 AP 隔离或访客网络不能是不能
VPN 主机开了全隧道，且客户端禁止本地网络能是不能

注意最后三行：它变「不能」的原因都不是拓扑，而是被隔离了或者目标主机自己拒绝了。所以排查问题时要按这个顺序问：

  1. 两台设备在不在同一个广播域？（没有 AP 隔离、没有 VLAN 划分、没跨 WAN 口）
  2. 是不是同一个网段？（掩码算一下）
  3. 目标主机那边有没有策略拦截？（防火墙、VPN 客户端、安全软件）

8.2　没有路由器，宽带网线直连交换机能上网吗

不能。交换机永远不会上网——它就是一根「多口排插」

你家能上网，是因为有一台设备在干三件事：① 拨号（拿公网 IP）、② NAT（把内网地址翻译成公网地址）、③ DHCP（给设备分地址）。这三件交换机一件都做不了。

你家的「宽带」是哪种直连交换机的结果原因
PPPoE 拨号（绝大多数家用）不能上网必须有设备提交账号密码去拨号，交换机不会拨。谁都没拿到 IP
ISP 直接给固定 IP / DHCP（专线）只有一台能用ISP 通常只给 1 个 IP、还常绑 MAC。且没有 NAT 没有防火墙，电脑直接暴露在公网
看着像交换机、其实是路由一体机能它有 WAN 口、能填宽带账号——本质是路由器，不叫交换机

如果某台电脑自己用系统自带功能拨号呢？那台电脑能上网（它拿到了公网 IP），但其他电脑还是不能——它们没有网关、没有 DNS。想让它们也上，那台电脑得再开「网络共享（ICS）」把自己当网关，也就是回到第 1 章讲的「借道」了。

怎么快速分辨

看它有没有 WAN 口、有没有能填宽带账号的管理界面。有，就是路由器。市面上很多小盒子既有多个 LAN 口又能填账号，它叫「无线路由器」，只是长得像交换机。

8.3　交换机能不能开 VPN

判断标准只有一条：这个设备有没有 IP 协议栈、能不能改自己的路由表、有没有转发能力。三条都满足，它才跑得动 VPN。

设备有 IP 协议栈和路由表能当 VPN 客户端没路由器时能带人上网
二层交换机没有不能不能
三层交换机有能能（需配 NAT）
家用无线路由器有能（看型号）能
软路由 / OpenWrt有能能
NAS（群晖、威联通）有能需额外配置

二层交换机为什么不行：它没有 IP 协议栈、没有路由表、也没有 CPU 去跑 VPN 客户端。它连 IP 包都看不懂，只认网卡地址（MAC），做的事就是「这个帧该从哪个口送出去」。

三层交换机为什么行：它有完整的 TCP/IP 栈和路由能力，企业级的（Cisco、H3C、华为）都支持 IPsec VPN，当客户端当服务端都行。

家用想「全屋走 VPN」的正确做法

① 用本身支持 VPN 客户端的路由器（不少家用型号有 OpenVPN / WireGuard 客户端功能）
② 刷 OpenWrt 固件
③ 加一台软路由做旁路由
④ 在 NAS 上跑 VPN 客户端，再把局域网网关指向它

WAN 口接 LAN 口是什么意思

级联 ≠ 桥接 · 双重 NAT 的代价 · 三种「桥接」说法的澄清

一句话结论：把路由器的 WAN 口接到另一台路由器的 LAN 口，这叫级联，结果是「双重 NAT」——两台路由器各管一个子网，NAT 做了两遍。它不是桥接。真正想让第二台路由器「只当交换机用」，要接的是它的 LAN 口，并且关掉它的 DHCP。

5.1　两种接法的对比

5.2　接 WAN 口的完整过程（双重 NAT）

假设电脑接在 R2 下面，地址是 192.168.2.10，要访问百度：

  1. 电脑发现目标不在本网段 → 交给自己的网关，也就是 R2 的 LAN 口 192.168.2.1。

  2. 第一次 NAT：R2 把源地址从 192.168.2.10 改成自己 WAN 口的地址 192.168.1.2，发给 R1。

  3. R1 收到一个源地址是 192.168.1.2 的包，它只知道这是自己内网的某台设备，照常处理。

  4. 第二次 NAT：R1 把源地址改成自己的公网地址，发往互联网。

  5. 回包反向走两遍：公网 → R1（还原一次）→ R2（再还原一次）→ 电脑。

影响具体表现
上网能不能通能，只是多了一层，延迟略微增加
上游能访问下游吗不能。R1 下面的设备访问不到 R2 下面的设备，因为 R2 的 NAT 把下游藏起来了
下游能访问上游吗能。单向可达
P2P / 游戏联机 / BT容易出问题。NAT 穿透要穿两层，成功率大幅下降
UPnP 自动端口映射通常失效，穿不过两层
端口映射（做服务器）必须在两层都做，非常麻烦

5.3　接 LAN 口的正确姿势

  1. 网线插 R1 的 LAN 口 → R2 的 LAN 口（注意不是 WAN 口，WAN 口空着不用）。

  2. 登录 R2 的管理页面，关闭 DHCP 服务器。这一步必须做，否则两个 DHCP 服务器会打架。

  3. 把 R2 自己的管理 IP 改成和 R1 同网段、但不会冲突的地址（比如 R1 是 192.168.1.1，R2 改成 192.168.1.2）。

  4. 结果：R2 退化成「交换机 + 无线 AP」，所有设备都在 192.168.1.0/24 里，互相都能看见，也没有双重 NAT。

5.4　三种「桥接」说法的澄清

中文语境里「桥接」这个词被用了三个不同的意思，混起来非常容易吵架。逐一说清楚：

说法真实含义属于哪一层典型场景
光猫桥接（Bridge Mode）关掉光猫的拨号和 NAT，只做光电转换，拨号交给路由器三层功能关闭，设备退化为「媒体转换器」想用自己的路由器拨号、拿公网 IP 时
无线桥接 / WDS两台无线路由器用无线连起来，扩展覆盖范围二层（WDS 可以做到同一广播域）家里信号覆盖不到另一个房间
路由器当交换机用LAN→LAN + 关 DHCP，关掉路由功能只留交换和无线三层功能关闭手头多一台路由器，想当交换机使
「WAN 口接 LAN 口」不是桥接的原因

桥接是二层概念：把两个网段合并成一个广播域，设备之间靠 MAC 直接通信，看起来像接在同一台交换机上。
WAN→LAN 是三层概念：两台路由器各维护一个子网，中间靠 IP 路由 + NAT 转发，广播不会穿过，两边的设备互不相识。
所以它叫「级联」，不叫桥接。

掩码、网关与广播

设备只做一个判断 · ARP 把 IP 翻译成 MAC · 广播是「对着一屋子人喊」

一句话结论：子网掩码决定「直接喊还是交给网关」，网关决定「交给谁」，广播是「还不知道跟谁说」时的通信方式。而设备自己从来不做复杂的路由决策——它只会做一个判断：目标和我是不是同一个网段。

6.1　子网掩码：把 IP 切成两半

IP 地址一共 32 位（IPv4），掩码的作用就是告诉你：这 32 位里，前多少位是「网络号」，剩下的是「主机号」。

IP 地址：  192.168.1.10
子网掩码： 255.255.255.0
          └─────┬────┘└─┬─┘
          网络号 192.168.1   主机号 10

等价写法： 192.168.1.10/24      ← /24 表示前 24 位是网络号

怎么判断两台设备是不是同一个网段

把两个 IP 分别和掩码做按位与运算，结果相同就是同网段：

192.168.1.10 AND 255.255.255.0 = 192.168.1.0
192.168.1.20 AND 255.255.255.0 = 192.168.1.0   ← 相同，同网段

192.168.2.10 AND 255.255.255.0 = 192.168.2.0   ← 不同，跨网段

6.3　网关：所有「不在本网段」的包的出口

  • 定义：默认路由的下一跳，通常就是路由器 LAN 口的地址（192.168.1.1）。
  • 作用：设备判断「这个目标不在我的网段」之后，唯一的动作就是把它交给网关。
  • 关键点：设备只配一个网关就够了，因为设备根本不做路由决策。真正复杂的选路，全部由路由器完成。
  • 没有网关会怎样：设备只能和自己同网段的设备通信，出不了门。这就是 APIPA 的状态。

一句话区分

IP 决定「送到哪个网络、哪台机器」，MAC 决定「这一跳具体交给哪块网卡」。IP 是收件地址，MAC 是投递到门牌号。

ARP：把 IP 翻译成 MAC 的过程

  1. A 要发数据给 192.168.1.20，先查自己的 ARP 缓存：这个 IP 的 MAC 是多少？

  2. 缓存里没有 → 广播一个 ARP 请求：「谁是 192.168.1.20？请告诉 192.168.1.10，我的 MAC 是 AA:AA:AA。」

  3. 交换机看到这是一个广播帧（目标 MAC 是 FF:FF:FF:FF:FF:FF），会从除来源端口之外的所有端口发出去。

  4. 192.168.1.20 收到后，单播回应：「我是，我的 MAC 是 BB:BB:BB。」

  5. A 把这个对应关系记进 ARP 缓存（Windows 通常缓存几分钟），然后开始正式发数据。

跨网段时 ARP 问的是谁

跨网段时，ARP 问的不是最终目标的 MAC，而是网关的 MAC。包先发给网关，由网关再去决定下一跳是谁。所以 ARP 广播永远出不了本网段——这是广播的天然边界。

6.5　广播是什么

  • 定义：目标 MAC 是 FF:FF:FF:FF:FF:FF 的帧，或者目标 IP 是网段内主机号全为 1 的地址（如 192.168.1.255）。
  • 交换机怎么处理：从除来源端口之外的所有端口转发出去。同一个广播域里的每一台设备都会收到。
  • 常见用途：
    • ARP 请求（找 MAC）
    • DHCP Discover（找服务器，因为此时设备还没有 IP，无法单播）
    • NetBIOS 名称解析（老式 Windows「网上邻居」）
  • 问题：广播多了会吃掉可观的带宽，严重时形成「广播风暴」，把交换机 CPU 打满、网络瘫痪。
  • 路由器默认隔离广播：广播不会穿过路由器。所以一个网段里的广播，另一个网段的设备是收不到的。
这就是「子网」存在的真正意义

把一个大网络切成多个小广播域，让每段里面的广播量可控。一个子网里设备越多，广播的绝对数量越大，效率越低。所以大型网络会划 VLAN、划子网，把每个域控制在合理规模。

互联网是怎么连起来的

逐跳转发 · BGP 交换路由 · 三件被忽略的事

一句话结论：是，互联网的连通性核心就是路由器逐跳转发 + BGP 交换路由。但要说得准确，还有三件事：送信号靠光传输设备，送内容常被 CDN 提前截住，同一个 IP 在多地同时存在靠 Anycast。

7.1　分层结构：从你家到目标服务器

7.2　核心机制：BGP 与逐跳转发

互联网由几万个自治系统（AS）组成。比如中国电信是 AS4134、中国联通是 AS4837、阿里云是 AS45102。每个 AS 通过 BGP（边界网关协议）向邻居宣告：「我这里有这些 IP 网段，要来的话交给我。」

  • 全球 IPv4 路由表约 95 万 ~ 100 万条，并且持续增长。
  • 每台路由器只关心一件事：「去往 X 网段，下一跳交给谁。」
  • 路由器之间不交换「完整地图」，只交换「这个方向能不能到」——这是互联网能扛住规模的秘诀。

一个包的完整旅程（访问 example.com）

  1. DNS 解析：先查浏览器缓存 → 系统缓存 → 运营商 DNS。都没有就去递归查询：根服务器 → .com 顶级域 → 权威服务器，最终拿到目标 IP（比如 93.184.216.34）。这一步本身也是走网络完成的。

  2. 你的电脑：判断目标不在本网段 → 交给网关。

  3. 家用路由器：做 NAT，把源地址换成公网 IP → 交给运营商的 BRAS。

  4. BRAS / 城域网：查路由表 → 送到省级核心。

  5. 省网核心 → 国家骨干：逐跳转发，可能经过 10~20 跳，中途可能跨 IXP（互联网交换中心）进入对方 AS。

  6. 对方网络的边界路由器：进入目标 AS，逐层下发：汇聚 → 接入 → 服务器。

  7. 回包：沿路返回，但路径可能和去程完全不同——因为 BGP 是单向选路的，去和回是两条独立的决策。

那「是否都靠路由器转发」的精确答案

方面靠什么说明
决定往哪走（选路）路由器逐跳查表，BGP 提供跨 AS 的路由信息
把信号送到几百公里外DWDM 光传输设备路由器负责「决策」，光设备负责「搬运」。路由器 → 光设备 → 光纤 → 光设备 → 路由器
内容实际从哪来CDN 边缘节点视频、图片、静态资源大多缓存在离你几十公里的节点，根本没走远
同一个 IP 全球可用Anycast8.8.8.8、1.1.1.1、根域名服务器：多地宣告同一 IP，BGP 把你导向最近的那个

所以更准确的说法是

互联网的连通性来自「路由器逐跳转发 + BGP 交换路由」；
互联网的物理传输来自「DWDM 光传输 + 海底光缆」；
互联网的实际体验被 CDN 和 Anycast 大量优化——很多流量根本没有走出你所在的城市。

从河南到河北：百万家庭的流量怎么过一根光纤

波分复用 · 统计复用 · 光纤到底算不算弱网

一句话结论：前提要修正两处。第一，光纤的带宽不是固定的——一根纤可以同时跑几十上百个波长，容量做到几十 Tbps。第二，百万家庭不会同时满速跑——运营商靠「统计复用」按概率卖带宽。所以这不是「把几十万 T 挤进一根纤」，而是「两层复用把需求削掉几个数量级」。

8.1　纠正前提一：光纤的容量不是固定的

扩容的三条路（从易到难）

手段做法周期是否需要挖沟
加波长两端各加一块板卡，启用空闲波长几天到几周不需要
加纤芯启用光缆里还没用的纤芯几天不需要
再铺光缆在原有路由上敷设新光缆几个月需要

这是光纤最重要的一点：扩容最常用的手段是「加波长」，完全不用动土。两端加设备，中间的玻璃和管沟一个字都不用改。

8.2　纠正前提二：百万家庭不会同时满速跑

这是运营商商业模式的基础，叫 统计复用（oversubscription，也叫收敛比）。

  • 假设每户签约 100 Mbps，但同一时刻真正跑满的概率极低，一般在 1%~10% 之间。
  • 所以一个 10 Gbps 的上联口可以挂几百户，收敛比常见 1:10 ~ 1:50，某些场景更高。
  • 这不是偷工减料，是全球通行的行业标准做法。
  • 依据是流量模型：绝大多数人大部分时间在刷网页、看视频（有缓冲，是突发性的），而不是持续满速下载。
那晚高峰为什么会卡

因为晚 8 到 10 点，并发率上升，实际需求接近或超过了上联口的容量。运营商的应对是 QoS 分级（优先保语音和视频）+ 持续扩容。所以你感觉「晚上卡」，本质上是收敛比在高峰时段不够用了，而不是光纤本身跑不动。

8.6　光纤算弱网吗

不算。恰恰相反——光纤是目前最好的传输介质。所谓「弱网」是终端侧的概念。

「弱网」真正指的是这些场景：

  • 移动网络的弱信号区（4G / 5G 边缘、地下车库、电梯里）
  • Wi-Fi 信号差、同频干扰严重
  • 高丢包、高抖动、高时延的链路
  • 卫星网络（时延高，还受天气影响）

真正的瓶颈从来不在骨干光纤上，而在这几处：

  1. 最后一公里：PON 端口拥塞（32 户共享 2.5 Gbps 下行）
  2. 运营商之间的互联带宽：跨网访问（电信 ↔ 联通）的历史遗留问题
  3. 服务器自身：CPU 处理能力、磁盘 IO、出口带宽
  4. 家里的 Wi-Fi：这才是绝大多数人真正感受到「慢」的地方
一句话记住

从河南到河北那根光纤，是全程最富余的一段。你感觉慢，大概率是最后 10 米那个无线路由器，或者你连的那台服务器本身就慢。
