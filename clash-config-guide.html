01配置文件分几层:一条数据的旅程

搞懂这张流水线,后面所有的疑问都会自动化解。Verge 的配置不是「一个文件」,而是一条加工链:

机场服务器 │ HTTPS 拉取 ▼ profiles/{uid}.yaml ← 订阅原文(proxies / proxy-groups / rules 都在里面) │ ├─▶ Merge.yaml 深度合并:改字段、加字段 ├─▶ Script.js 脚本处理:用 JS 任意改 config 对象 ├─▶ rules.yaml prepend / append / delete 规则 ├─▶ proxies.yaml 增删节点 └─▶ groups.yaml 增删策略组 │ ▼ clash-verge.yaml ← Verge 生成的最终文件(0.5 MB,内核真正读的) │ + config.yaml(骨架/tun) ▼ verge-mihomo 内核进程 │ ├─▶ 本地代理端口 7897(mixed-port) ├─▶ 系统代理 / TUN 虚拟网卡 Mihomo └─▶ 控制接口:Windows 命名管道

关键点:订阅可以整体替换,你的自定义不会丢。因为你的改动写在「增强槽」里,而槽位独立于订阅文件存在。订阅更新时只覆盖 profiles/{uid}.yaml,槽位文件岿然不动。

为什么要在意这个结构

很多人改配置的方式是「打开订阅文件直接改」—— 下次机场更新订阅,改动全被冲掉。正确姿势是写进 Merge 或 rules 槽位。第 7 章会给你现成的写法。

02全局字段逐条讲解

先把你贴的那段拆开。这些是整个代理程序的行为开关,不涉及具体节点。

mixed-port7890 → 实际 7897 「混合端口」。同一个端口同时说 HTTP 代理和 SOCKS5 代理两种协议,程序用哪个都行。老配置会分成 port(HTTP)和 socks-port(SOCKS5)两个,现在没必要了。
allow-lanfalse 是否允许局域网其他设备连你这个代理。开 true 后手机、平板可以填你电脑 IP 来上网,但同时把代理暴露到了内网 —— 公共 WiFi 下别开。

moderule 运行模式,三选一:

global 全部流量走一个代理,规则失效
direct 全部直连,等于关了代理
log-levelinfo 内核日志级别,从少到多:silent → error → warning → info → debug。排查问题时临时开 debug,平时 info 足够,debug 会疯狂写盘。
external-controller'127.0.0.1:9090' 「外部控制器」= 一个 RESTful API 端口。Clash 的各种图形面板(Yacd、MetaCubeXD)、手机遥控都是连它。填 0.0.0.0:9090 会让同网段所有人都能控你的代理,只填 127.0.0.1。

tcp-concurrenttrue 「TCP 并发连接」。一个域名可能解析出多个 IP(比如 CDN),开启后内核同时向所有 IP 发起连接,用最先成功的那个,掐掉抖动的那个。对首包速度有实在的改善。
ipv6true 内核是否接受 IPv6 流量。⚠️ 你家宽带若 IPv6 不通,开着只会让解析多绕一圈。

03proxies:节点是什么样子的

proxies 是一个列表,每个元素就是一台「能帮你翻墙的服务器」。你的机场A订阅里有几十个节点。下面是你订阅里真实存在的两种,密码已打码:

样本 A:Shadowsocks 节点(你订阅里的主力)

# profiles/profileA.yaml 第 35 行(单行流式写法)
- {name: 🇭🇰 香港-A01, server: hk01.node.example.com,
   port: 19272, type: ss, cipher: aes-256-gcm,
   password: ***打码***, udp: true}
字段含义
name节点显示名,必须唯一。策略组的 proxies 列表就是靠这个名字引用的 → 所以改名会导致策略组引用失效
type协议类型。ss = Shadowsocks
server / port服务器地址 / 端口
cipher加密方式。SS 专属字段
password密码。SS 专属字段
udp是否允许 UDP 走这个节点。默认 false。不开的话游戏、QUIC、部分视频通话会走不了代理

样本 B:VMess 节点(带 WebSocket 伪装)

# profiles/profileA.yaml 第 53 行
- {name: 🇭🇰 香港-A02 | IEPL, server: hk10.node.example.com,
   port: 13483, type: vmess, uuid: ***打码***, alterId: 1,
   cipher: auto, tls: false, skip-cert-verify: false,
   network: ws,
   ws-opts: {path: /, headers: {Host: cdn.example.com}},
   udp: true}
字段含义
uuidVMess/VLESS 的用户身份标识,相当于用户名+密码合体
alterId旧版 VMess 的额外 ID。现代服务端基本都用 0 或 1
cipherVMess 的加密方式,auto = 自动协商
network传输层:可填 ws(WebSocket)、grpc、h2、http。不填则走裸 TCP
ws-opts.pathWebSocket 路径
ws-opts.headers.Host伪装请求的 Host 头 —— 让流量看起来像在访问某个正常网站,这是「伪装」的核心
tls / sni / skip-cert-verify是否启用 TLS / TLS 的域名 / 是否跳过证书校验
节点名里的 x0.01 / x0.8 / x1.5 / x2 不是配置字段

那是机场的流量计费倍率。用一次「x2」节点,后台按 2 倍扣流量;「x0.01」几乎不扣,所以标着「下载专用」—— 适合 BT、大文件。这纯粹是名字里的文字,内核不认识它。

策略组的完整字段

proxy-groups:
  - name: 🔰 选择节点
    type: select
    proxies:                      # 引用节点名或别的策略组名
      - 🇭🇰 香港-A01
      - 🇯🇵 日本W01 | IEPL
      - DIRECT                    # 内置:直连
      - REJECT                    # 内置:拒绝连接
    url: 'https://www.gstatic.com/generate_204'   # 健康检查地址
    interval: 300               # 每 300 秒测一次
    lazy: true                  # 懒测:当前没在用就不测,省资源
    tolerance: 50               # 延迟差小于 50ms 不切节点(url-test 用)
    timeout: 5000              # 单次测速超时(毫秒)
    disable-udp: false          # 是否对本组禁用 UDP
    filter: "(?i)港|hk|hongkong"      # 从 provider 里按名字筛节点
    exclude-filter: "美|日"            # 反向排除
    icon: https://example.com/hk.png  # 面板显示图标
三个内置值,写在 proxies 列表里当普通成员用
  • DIRECT —— 直连,不走代理
  • REJECT —— 拒绝,连接被丢弃(广告拦截靠它)
  • GLOBAL —— 内置的全局组,mode: global 时用它

成员还能从哪来(不只是一个一个列)

  • proxies —— 显式列出节点名 / 其他策略组名
  • use —— 引用 proxy-providers(订阅提供者)的名字,把整个订阅的节点拉进来
  • include-all-proxies: true —— 自动包含所有节点,不用手写
  • include-all-providers: true —— 自动包含所有 provider
  • filter / exclude-filter / exclude-type —— 对上面自动包含的结果做筛选

为什么重要:订阅节点会变(机场加机器、删机器)。用 include-all-proxies + filter,机场怎么变你的组都自动跟上,不用改配置。

no-resolve 到底是什么(高频疑问)

IP 类规则(IP-CIDR、GEOIP)要判断「目标 IP 属不属于这个网段」,但代理拿到的通常只是域名。于是内核必须先做一次 DNS 解析拿到 IP —— 这一步会引入延迟,还可能把域名提前暴露给本地 DNS。

no-resolve 就是告诉内核:这条规则别为了它去解析 DNS。解析不出来就跳过这条、继续往下走。

no-resolve 有个坑

官方文档写明:如果更早的规则已经触发过 DNS 解析,那么结果会被缓存,后面的 no-resolve 规则照样能匹配到。也就是说 no-resolve 只能阻止「主动去解析」,拦不住「已经解析过的结果」。它不是隐私开关。

06DNS 专题:你问的「里面的 dns 是什么意思」

这是整份配置里最反直觉的部分。一句话先给结论:

为什么代理软件要自己管 DNS

正常上网时,DNS 解析由操作系统完成。但在代理场景下这会出问题:你访问 youtube.com,如果系统先把它解析成真实 IP,再把这个 IP 交给代理 —— 那这次解析已经暴露给了本地 DNS 服务器(可能被污染、被记录)。

所以 Clash 把解析权收上来自己管:由内核决定「这个域名用哪个 DNS 解析、要不要走代理去解析」。这就是 dns: 段存在的意义。

核心概念:enhanced-mode 的两种模式

fake-ip(你在用)redir-host
返回给程序什么一个假 IP(取自 198.18.0.1/16),同时记下域名↔假IP 的映射真实的解析结果
后续怎么工作程序连假 IP → 内核查映射得知真实域名 → 按域名匹配规则 → 再真正解析拿着真实 IP 去匹配 IP 规则
速度快,省掉一次真实解析的等待慢,依赖真实 DNS 质量
规则匹配精度高 —— 因为能拿到域名,可以精确按域名分流只能靠 IP,域名规则要靠解析
代价部分程序对假 IP 不适应(局域网设备发现、P2P、部分游戏),需要靠 fake-ip-filter 放行可能有 DNS 污染、解析慢
典型搭配TUN 模式系统代理模式

function main(config, profileName) {

另外还有「本地配置」:新建或拖拽自己的 yaml 文件进去,不走网络。

A概念地基:协议分层与常见误区

这一章回答的是「为什么我看不懂配置」。根源通常只有一个:把三个不同层次的东西当成了同一层。先建立骨架,后面所有细节自动归位。

A1 · 先分清「协议」这个词的四个层次

你说「只知道 HTTP 和 WebSocket」—— 其实这两个就不在同一层。网络里「协议」是个被滥用的词,至少要分成四类:

层次代表管什么
传输层协议TCP · UDP数据怎么在网络上搬运。TCP 可靠有握手,UDP 快但不管丢包
应用层协议HTTP · WebSocket · gRPC · QUIC数据的表达格式。浏览器说 HTTP,实时推送用 WebSocket
代理协议(隧道协议)SS · SSR · VMess · VLESS · Trojan · Hysteria2客户端与服务端之间约定的握手 + 认证 + 加密封装方式。你配置里的 type 就是它
VPN 协议WireGuard · OpenVPN · IPsec在网络层建隧道,系统里出现一块虚拟网卡
澄清:SS / VMess 不是 VPN 协议

你的直觉「它们应该不是网络协议,是 VPN 协议」—— 前半句对,后半句不对。它们是「代理协议」,不是 VPN 协议。两者机制完全不同:

VPN代理(SS/VMess)
工作层次网络层,接管整个网络栈应用层,由程序主动把流量交出去
流量范围全部流量自动进去,你没法挑只转发你指定的流量(通过 socks/http 接口进)
系统表现多一块虚拟网卡默认什么都不变,程序要知道代理地址才走

之所以大家混着叫,是因为效果像。Clash 的 TUN 模式就是用虚拟网卡把代理「伪装」成 VPN 的效果 —— 但底层机制仍是代理转发,不是真正的加密隧道。这也是为什么开 TUN 后不支持代理的程序(游戏、命令行)也能走代理了。

A2 · 你那个 server 域名:没有加密,但确实「多级」

这就是「为什么 server 填域名而不是 IP」的实证答案
  • 智能调度 —— 不同地区/运营商的用户解析到不同入口 IP,自动选最优线路
  • 容灾 —— 某个入口挂了,改一条 GTM 记录就行

我刚才就是用明文 nslookup 查到整条链的 —— 任何人拿这个域名去查,都能查到它指向哪。DNS 查询默认是明文的。

A3 · 「节点名写香港,IP 却在中国移动广州」是怎么回事

这个发现值得单独说,因为它解释了节点名里的一个缩写。你订阅里大量节点带着 | IEPL 后缀:

  • IEPL = International Ethernet Private Line(国际以太网专线)
  • 链路是:你 → 国内中转入口(广州移动,延迟低、不易被干扰)→ 机场内部专线 → 香港出口

所以你解析到的那个 IP 是入口,不是出口。这也正是域名里那个 entry 的含义。带 IEPL 的节点通常比直连的贵(成本高),但晚高峰更稳 —— 你的订阅里 | IEPL 节点确实占了多数,这是好线路的标志。

cipher 是加密算法,Shadowsocks 系协议专有。mihomo 支持 40 多种,但实际只需记住三档:

A6 · udp 是什么意思,设成 true 会怎样

UDP 是和 TCP 并列的传输层协议。核心区别一句话:

TCPUDP
建连接要三次握手不握手,直接发
丢包自动重传,保证到达丢了就丢了,不重传
顺序保证不乱序不保证
速度慢一点但可靠快,牺牲可靠性
谁在用网页(HTTP/HTTPS)、下载、SSHDNS 查询 · QUIC/HTTP/3 · 在线游戏 · 语音视频通话 · BT

代理配置里的 udp 字段问的是:允许 UDP 流量经过这个节点吗?

设成 true 之后会怎么样

  • 好的方面 —— 游戏联机、Discord/Teams 语音、走 QUIC 的网站(不少 Google/YouTube 流量走 HTTP/3 即 QUIC)都能正常走代理了
  • 代价 —— UDP 转发需要服务端也开启 UDP relay,客户端开了服务端没开等于白开;另外 UDP 流量会计入你的流量消耗
  • 不设(默认 false) —— UDP 流量不走这个节点。而官方有个明确行为:如果当前规则指向的节点不支持 UDP,内核会继续向下匹配规则,而不是直接失败

判断标准只要你还玩游戏、用语音软件,就应该用带 udp: true 的节点。你的订阅里节点基本都写了 udp: true,这点是好的。

A7 · 为什么 VMess 有 network,Shadowsocks 没有

这是设计哲学的差别,不是能力差别。SS 也能伪装,只是换了个地方写。

VMess / VLESS / TrojanShadowsocks

想伪装成网页怎么办改 network: ws + ws-opts挂一个 plugin(插件)

SS 的伪装长这样 —— 注意字段位置完全不同

# SS 的做法:用 plugin 挂伪装层
- name: my-ss

  server: example.com
  cipher: aes-256-gcm
  plugin: v2ray-plugin          # ← 伪装能力在这里

  plugin: obfs
  plugin-opts:
    mode: tls
    host: bing.com

mihomo 支持的 SS 插件共有 7 种:obfs · v2ray-plugin · gost-plugin · shadow-tls · restls · kcptun · jls。其中 shadow-tls、restls、jls 属于新一代 TLS 伪装方案,需要配合 client-fingerprint 使用。

所以你那两个问题的答案是同一个

「为什么 VMess 有 network、SS 没有」 → 因为 VMess 把传输层做成了可配置字段,SS 把伪装做成了外部插件。
「为什么 ws-opts.path 和 Host 只有 VMess 这么写」 → 因为那是传输层的参数,只有支持可插拔传输层的协议才有。SS 的等价物是 plugin-opts.path 和 plugin-opts.host。

功能上两者等价 —— 都是让流量看起来像在访问 bing.com。

A9 · 用 TCP 有什么风险

风险不在 TCP 本身 —— TCP 很好。问题在于裸 TCP 上的代理流量特征太明显,能被逐层识别:

#被识别的点说明
1SNI 明文TLS 握手的 ClientHello 里,sni 是明文的。中间设备直接看到你要访问哪个域名(除非用 ECH)
2TLS 指纹不同软件发的 ClientHello 特征不同(密码套件顺序、扩展顺序)。Go 程序写的 TLS 和 Chrome 写的长得不一样,一眼能认出来
3主动探测防火墙主动连你的服务器,发个正常请求看它怎么回应。老 SS 会直接返回错误 → 暴露「这是个代理」
4TLS-in-TLS 检测你的代理流量套了 TLS,里面又是访问网站的 TLS。两层 TLS 的包长分布有独特特征
5流量时序特征包的大小、发送间隔、上下行比例,都能做机器学习分类

对应的解法,前面 A4 已经讲过主线(加密 → 混淆 → 伪装 → 借壳)。这里补两个具体手段:

  • 让 TLS 指纹像浏览器 —— client-fingerprint: chrome,让 mihomo 的握手和 Chrome 一模一样。你的配置里没有这一项,因为机场的 SS 节点用不上
  • Reality —— 直接借用真实网站的握手,探测者连上来看到的是那个真实网站

A11 · 浏览器说「不安全」、感觉「被监视」,跟这些有关系吗

要拆成三件完全不同的事,混在一起会白费功夫:

(1) 地址栏显示「不安全」

= 你访问的网站用的是 HTTP 明文,或它的 HTTPS 证书有问题。
这与代理完全无关,是那个网站自己的配置。你去翻 Clash 配置是找错方向了。

(2) HTTPS 证书警告页(「您的连接不是私密连接」)

可能原因:证书过期、证书域名与访问域名不匹配、自签证书。
这跟 skip-cert-verify 无关 —— 那个字段管的是「你的客户端要不要校验代理服务器」,不是「浏览器要不要校验网站」。两者是独立的两段 TLS。

但有一种情况值得警惕:某个网站平时正常,一开代理就报证书错误 → 那说明节点可能在做 TLS 中间人,或者节点的 CDN 配置有问题。这时候应该换节点。

(3) 「被监视」的感觉 —— 这部分有真实基础

  • DNS 查询是明文的(除非用 DoH/DoT):你的宽带运营商能看到你解析了哪些域名
  • SNI 是明文的(除非用 ECH):即使内容加密,运营商也知道你在访问哪个网站
  • 更严重的场景:skip-cert-verify: true + 恶意节点 → 节点持有者可以中间人你的流量,那时真的会被看光

准确的结论是:在普通代理模式下,ISP 能看到「你去了哪」,看不到「你在那做了什么」。

这也是代理和 VPN 的一个重要差别:VPN 把 DNS 也收进隧道,而代理模式下 DNS 可能仍然走本地。

怎么改善

  1. 开启 fake-ip + DoH/DoT —— 你已经配了 DoH,但开关关着(见第 6 章和第 10 章第 1 条)
  2. 尽量不用 skip-cert-verify: true,改用 fingerprint
  3. 免费公开节点不登录敏感账号
  4. 真要高隐私,那是 VPN + Tor 的领域,不是代理能解决的

A12 · 一台 VPS 能部署多个节点吗

能,而且机场基本都这么干。一台 VPS 可以:

  • 同一协议跑多个端口(每个端口 = 配置里的一个「节点」)
  • 多个协议共存 —— ss 一个端口、vmess+ws 一个端口、hysteria2 一个端口
  • 多用户各自独立配置
但必须理解这个限制,否则会白折腾

同一台 VPS 上的所有节点,共享同一份带宽和同一个 IP。

  • ❌ 「10 个节点」≠「10 倍带宽」—— 带宽是物理的,一个节点跑满其他都得等
  • ❌ 那个 IP 被封,这台机器上的所有节点一起失效
  • ✅ 真正的冗余来自多台 VPS + 多个地区 + 多个 IP 段

那机场为什么给一台机器配多种 type?

为了应对不同的封锁策略,不是为了提速:

  • 有的网络环境封 SS 但不封 VMess + ws
  • 有的环境封 UDP —— 那 hysteria2 / tuic 就全废了,只能退回 TCP 系
  • 有的环境对特定端口不友好(非 443 端口常被掐)

所以多协议 = 多套备用方案。这是「可用性冗余」,不是「带宽冗余」。

你自己一台 VPS 的建议
  • 一个主协议 + 一个备用端口,足够了。推荐 VLESS + Reality(抗识别最强)或 Hysteria2(弱网性能最好)
  • 不必堆协议 —— 你是单人使用,「抗封锁多样性」的意义不大
  • 把精力花在选对协议 + 配好 TLS 伪装上,比堆五个协议有用得多

A13 · 路由器故障时 QQ 能上、网页打不开,跟 UDP 有关系吗

有间接关系,但根源通常不是 UDP。先说为什么 QQ 能上:

QQ浏览器
怎么找到服务器客户端内置服务器 IP 列表并会缓存,直接连 IP你输入域名 → 必须先做 DNS 解析 → 才知道连哪
DNS 挂掉时照常工作全部打不开

所以「QQ 能用、网页全废」这个组合,是 DNS 故障的经典特征。

UDP 在其中的角色

DNS 查询默认走 UDP 53 端口。路由器故障如果破坏了 UDP 转发(NAT 表、连接跟踪、防火墙规则),DNS 就失败,于是网页全废。

所以链路是通的:UDP 异常 → DNS 失败 → 网页打不开。但把锅单独扣给 UDP 会误判 —— 准确说法是「跟 DNS 有关,而 DNS 恰好依赖 UDP」。

其他可能原因(按实际概率排)

  1. DNS 服务器故障 —— 最常见。路由器上的 DNS 转发进程挂了
  2. MTU 不匹配 —— 网页要传大包(大 HTML、HTTPS 握手),QQ 用的小包。MTU 不对会导致大包被丢,表现为「QQ 能上,网页卡死或白屏」
  3. NAT / 连接跟踪表满 —— 路由器会话表溢出,新连接建不上,但 QQ 的已有连接还活着
  4. 路由器 TCP 处理异常 —— 有状态检测的设备对新建 TCP 连接处理出错

怎么判定(下次故障时照做)

nslookup www.baidu.com            # 能解析 → DNS 没问题,往 MTU 方向查
nslookup www.baidu.com 8.8.8.8    # 换公共 DNS 能解析 → 路由器的 DNS 有问题
ping -f -l 1472 8.8.8.8          # 测 MTU;提示"需要拆分"则 MTU 偏大

修复手段:

  • 手动把 DNS 设为 223.5.5.5 / 8.8.8.8(绕开路由器 DNS 转发)
  • 调低 MTU(常见值 1480 / 1452)
  • 重启路由器清空 NAT 表
给你留一个判断口诀

QQ 能上、网页打不开 → 先怀疑 DNS,再怀疑 MTU。
如果连 QQ 也上不了、但局域网设备之间互通 → 那是 WAN 侧或 PPPoE 断了,跟 UDP 无关。

B网络体系:VPN、代理、专线与流量可见性

附录 A 解决的是「配置文件里的字段是什么意思」。这一章往下挖一层,回答的是「这套东西在整个网络里处于什么位置、谁看得见什么」。八个问题看着散,实际上都可以归到三根主轴上:

主轴决定什么涉及问题
介入层次VPN / 代理 / TUN 各自在网络栈的哪一层动手问题 1、2
控制点DNS 与专线决定了「找谁、怎么过去」问题 3、4、5
可见性加解密的终点在哪,决定谁能看到什么问题 6、7、8
一句话抓住第三根主轴(后面反复用到)

判断「谁能看到什么」,只看一件事:加解密的终点在哪台机器上。

  • HTTPS 的终点在网站 → 路由器看不到,网站能看到
  • DoH 的终点在 DoH 服务商 → 路由器看不到,DoH 服务商能看到(信任只是转移了)
  • 代理的终点在代理服务器 → 路由器看不到,代理服务商能看到(它知道你的真实目标)

所以「用代理更安全」要加限定:你不是让谁都看不见,而是把信任从 ISP 转移给了代理服务商。

B0 · 先把名词摆正:这些词各自在哪一层

「梯子」「VPN」「代理」在日常口语里被混用,但技术上它们不是一类东西。先上总表:

先把一个误会清掉

你之前问过「SS 和 SSR 应该不是网络协议,应该是 VPN 协议吧」——两个都不是。

  • SS / SSR / VMess / VLESS / Trojan 是「代理协议」,工作在应用层
  • 它们的共同点是:定义了一套「客户端把请求交给它、它替你转发」的格式,不碰内核路由
  • 它们不是 VPN 协议(VPN 协议是 OpenVPN / WireGuard / IPSec 这一类,要在网络层建隧道)
  • 它们也不是传输协议(那是 TCP/UDP/QUIC 的事)

所以准确的说法是:「翻墙工具」通常 = 一个代理协议的客户端 + 可选的一层 TUN 伪装。

B1 · VPN 与代理的本质区别:差在「介入层次」

你原来的判断是对的,这里把它讲透。两者的差别不是「强度」,而是在协议栈的哪一层动手。一层之差,带来下面所有差异。

数据包走的路,完全不同

VPN(网络层拦截) 应用 → 系统 TCP/IP 栈 → 查路由表 → [虚拟网卡] → VPN 客户端加密 → 物理网卡 → 公网 → VPN 服务器解密 → 目标 ↑ 路由表把 0.0.0.0/0 指向这里,应用完全不知道 代理(应用层转交) 应用 → [SOCKS5 / HTTP 接口 127.0.0.1:7897] → 代理客户端 → 物理网卡 → 公网 → 代理服务器 → 目标 ↑ 应用必须主动把连接交给这个端口,不交就不走

为什么 VPN 需要虚拟网卡,代理不需要

VPN 的目标是「接管所有流量」——包括那些不配合的应用、系统服务、后台更新。要在网络层拦住它们,唯一的办法是插一块网卡,然后把默认路由指过去:内核一查路由表,「目标不在本地 → 走 VPN 网卡」,包就自然落进 VPN 客户端手里。

代理的目标是「转交一个连接」——应用连本地端口,代理进程接管这条连接,替它去连真目标。「接管」发生在应用层,不需要碰内核路由,所以不用网卡。

那 Clash 的 TUN 到底是什么

你原来的说法很准确,补一个更机械的描述:

TUN = 「把代理提升到网络层」的手法

mihomo 自己建一块 TUN 网卡、写路由表,把内核送上来的 IP 包解析还原成 TCP/UDP 流,然后交给它原本的代理逻辑去分流、去转发。

所以对外表现像 VPN(全流量、无需应用配合),内部仍然是「转发 + 代理」,不是 VPN 那种端到端的加密隧道。

再补一个容易混的点:TUN 处理 L3(IP 包),TAP 处理 L2(以太帧)。TAP 能传非 IP 协议(用于桥接),OpenVPN 两种都支持,Clash 只用 TUN。

第一组:系统代理 vs TUN —— 同一件事的两种实现

B3 · TUN 为什么会打坏公司 OpenVPN

这是你实际问题里最有价值的一个。先说结论:这是一场「路由表争夺战」,外加驱动层和 DNS 层的连带损伤。不是 Clash「坏了」,而是两个都自称「默认出口」的程序在同一台机器上打架。

冲突机制,分四层

第一层:路由表 —— 谁写得更具体、谁后写,谁赢

OpenVPN 连上后会创建虚拟网卡并写路由,两种模式:

  • 全局模式:写 0.0.0.0/0 → VPN 网关,所有流量进隧道
  • 分裂隧道(split tunnel):只写内网网段,如 10.8.0.0/24 → VPN、172.16.0.0/12 → VPN

Clash TUN 开 auto-route: true 时,官方文档的说明是「自动设置全局路由,可以自动将全局流量路由进入 tun 网卡」。它实现的方式很讲究——用 0.0.0.0/1 + 128.0.0.0/1 这对「半默认路由」,两条合起来覆盖全部 IPv4。

为什么用两条 /1 而不是一条 /0

因为路由表按 最长前缀匹配优先:/1 比 /0 更「具体」,所以能盖过任何已存在的 /0 默认路由,而不用去删它。同一前缀时才比 metric(跃点数),小的优先。

这是有意设计的「抢路但不破坏」手法——但副作用是:它会盖掉公司 VPN 的全局默认路由。

三种结局:

组合结果
公司 VPN 是分裂隧道,Clash 加 /1基本可用 内网 10.8.0.0/24 比 /1 更具体,仍走 VPN;其余走 Clash
公司 VPN 是全局模式,Clash 加 /1内网断 Clash 的 /1 比 /0 更具体,把公司隧道架空
先开 Clash 再加公司 VPN(全局)可能环路 包进 Clash TUN → 出站又匹配 VPN 默认路由 → 进 VPN 隧道 → 又匹配 Clash → 死循环(全断网)

这就解释了你可能遇到的「先开 A 后开 B 能行,反过来就不行」——本质是谁后写路由谁生效,以及写出来的组合是否自洽。

第二层:DNS 劫持 —— 内网域名被掐断

Clash TUN 会开 dns-hijack,把发往任何地址的 53 端口查询全部截获,交给自己的 DNS 模块。问题在于:

  • 公司内网 DNS(比如 10.8.0.1)会解析只在内网存在的域名(如 git.corp.local)
  • 被劫持后,这些查询被送进 Clash 的 DNS → 拿去问公网 DNS → 查不到
  • 表现:能 ping 通内网 IP,但用域名访问内网系统全部失败

第三层:虚拟网卡驱动与接口绑定

这一层才是「为什么要重装」的答案。

  • Windows 上 Clash TUN 用 wintun 驱动创建适配器(名字通常是 Mihomo 或 Meta)
  • OpenVPN 老版本用 tap-windows6,新版本(2.5+)也用 wintun —— 同源驱动,更容易互相干扰
  • 麻烦点:
    • 适配器名 / 接口索引(ifIndex)会因驱动重载或重启而重排 → OpenVPN 的 dev 绑定漂移
    • Clash 每次开关 TUN 都创建/销毁适配器 → 可能顶着 OpenVPN 的绑定
    • 路由表里留下指向已消失接口的残留路由 → 包被送进黑洞
    • strict-route 在 Windows 上还会加防火墙规则,阻断多宿主 DNS 解析(文档明确提到可能影响 VirtualBox 这类应用)

第四层:为什么「重装才恢复」

因为坏的不是一个点,而是三处叠加:适配器名被顶掉 + OpenVPN 服务注册的驱动状态异常 + 路由表残留。用户层的「重启 Clash Service」只能触发路由重排,看着像好了,下次再开又坏。

干净恢复的顺序(别跳步)
  1. 关闭 Clash 的 TUN
  2. 完全退出 Clash(连内核一起退,不是最小化)
  3. 管理员执行 route print,对比看残留路由是否还在
  4. 禁用再启用网络适配器(或重启)
  5. 重连公司 OpenVPN

若走到这一步还不行,再考虑重装 OpenVPN 客户端。先别急着重装 —— 十有八九是路由残留。

正确的共存姿势(按推荐度排)

B4 · 域名解析:nslookup、NS 记录、GTM 与智能调度

「明文 nslookup」是什么意思

nslookup 是最原始的 DNS 查询工具。它做的事情是:向 DNS 服务器发一个 UDP 53 端口的明文查询包,问「某域名的 A 记录是什么」,服务器明文回答。

「明文」指两件事都不加密:你问的是哪个域名,以及回答的 IP 是多少。路径上任何一台设备(你的路由器、ISP 的 DNS)都看得见。

这也是为什么「我用 nslookup 就能查到」——它本来就没有任何加密,任何人都能查。想加密得用 DoH / DoT(DNS over HTTPS / TLS)。

NS 记录是什么

NS(Name Server)记录回答的是:「这个域名由哪台服务器负责解析(权威服务器)」。

DNS 是分层的:根 → 顶级域(.com / .cn / .xyz)→ 二级域 → …… 每一层都用 NS 记录指向下一层。查你那个域名的 NS,会看到指向 vip7.alidns.com 这类阿里云 DNS —— 这说明这个域名托管在阿里云,而不是「域名被加密了」。

完整解析链条(拿你那个域名走一遍)

客户端问:hk01.node.example.com 的 IP 是多少? ↓ 本地递归 DNS(没有缓存) 根服务器 → 「去问 .xyz 的 NS」 .xyz 权威 → 「去问该二级域的 NS」 权威 NS → 返回 CNAME: gtm-hk.node-example.com ↓ 再查 gtm-hk.node-example.com 权威 NS → 返回 A 记录: 203.0.113.10

gtm-hk 这个前缀里的 GTM,就是下一个问题的答案。

GTM 为什么能解释「server 不填 IP」

GTM = Global Traffic Manager,本质是一个「会思考的权威 DNS 服务器」。阿里云官方文档把它讲得很明确,三个关键点:

  1. GTM 工作在 DNS 层,通过 DNS 返回一个 IP。它不是代理,不是网关,也不是应用接入服务,看不到客户端与服务之间的网络流量。
  2. 你查域名时,它不是查表返回固定 IP,而是走一条评估链。
  3. 因为决策是每次查询实时做的,所以能自动容灾、就近接入。
GTM 的五步评估链 ① 查询到达 → 判断你是谁(按 DNS 请求的来源 IP,识别地理位置 + 运营商) ② 健康过滤 → 把不健康的地址摘掉(多地点 ping / TCP / HTTP 探测) ③ 选择范围 → 按策略(就近 / 权重 / 轮询 / 顺序)选出地址池 ④ 选出地址 → 池内按算法挑一个 IP ⑤ 返回答案 → 把 IP 给你

于是「不填 IP」的四个好处都有了机制解释:

好处实现机制
方便换服务器改 DNS 记录即可,客户端配置一个字都不用动
自动容灾健康检查发现故障 → 摘除地址 → 你自然拿到别的 IP
就近接入按查询来源归属选入口:广东的解析到广东,北京的解析到北京
抗封IP 被封或被污染 → 换记录,无需通知任何用户

智能调度的两种「就近」

类型依据说明
静态就近预设拓扑规则:客户端属于哪个国家 / 洲 / 运营商 / ASN规则固定,按「谁归谁管」分配
动态就近实测到客户端的网络性能(时延 / 丢包 / 跳数)只在特定模式下可用,且是基于 DNS 请求来源探测,不是探你的实时链路
一个容易忽略的真相:切换不是瞬时的

GTM 改了答案,但你和中间递归 DNS 还缓存着旧答案,要等 TTL 过期才会用新的。所以抗封场景会用很短的 TTL(60~300 秒),而普通网站常用 3600 秒。

换句话说:「换 IP 无感」说的是「你不用改配置」,不是「立刻生效」。

代价(要说的另一面)

  • DNS 查询本身是明文的 —— 谁在查、查什么,路径上可见(除非用 DoH/DoT)
  • 域名持有方(机场)能看到「有人查了这个域名」,虽然不知道具体是谁
  • 多一跳解析,多几十毫秒

B5 · IEPL 国际以太网专线:为什么贵,以及「合法」的边界

是什么

IEPL = International Ethernet Private Line,国际以太网专线。运营商提供的点对点二层专线:你在广州的机房和香港的机房之间,拉一条「看起来像一根直连网线」的通路。

三个关键特征:

  • 不过公网 —— 不经过普通互联网路由,走运营商自建的国际传输网
  • 独占带宽 —— 买 10M 就是 10M,不与别人抢
  • 点对点二层 —— 像一根拉长的网线(Ethernet),是「通路」不是「上网服务」

顺带区分几个常在订阅里看到的词:

术语全称 / 含义关系
IPLCInternational Private Leased Circuit更老、更贵,传统上是 TDM/SDH 电路
IEPLInternational Ethernet Private LineIPLC 的以太网版本,更灵活
MPLS VPN共享骨干上的逻辑隔离比 IEPL 便宜,隔离性略弱
SD-WAN软件定义广域网,用公网 + 优化调度这几年主流,成本低得多

价格层级(贵 → 便宜):IPLC > IEPL > MPLS VPN > SD-WAN > 普通国际公网优化。

为什么贵

成本来源说明
独占带宽不是共享,1M 就是 1M 的资源被占住
跨境光缆资源稀缺国际海缆容量有限,热门方向(香港 / 日本 / 新加坡 / 美国)尤其紧张
需要国际出入口局资质中国只有三大运营商持有国际通信出入口局牌照
SLA 保障承诺可用率、时延、丢包率
企业级属性带固定 IP、二层通道、可审计可追溯

合规性:必须分两层说,别混

第一层:IEPL 这个产品本身 = 合法

中国电信、中国联通、中国移动持有国家颁发的国际通信出入口局牌照。IEPL 是它们正常的商业产品。企业正常签约使用,完全合规。

第二层:谁在用、怎么用 = 决定是否合规

监管要求(工信部 + 各地通信管理局)对国际专线实行实名审批制:

  • 主体:必须是依法注册的企业法人,个人不能申请(个体工商户也不行)
  • 用途:必须真实且正当(跨境电商、跨国协同办公、ERP 数据同步等)
  • 「三不原则」——申请时须承诺:
    1. 不转租:仅供本企业(含母子公司)内部使用,不得转租 / 分销给第三方
    2. 不提供公网接入:不得利用该线路为外部人员提供「翻墙」或公网接入服务
    3. 不用于非法内容:严禁传输违法违规内容

所以,对你那个问题的直接回答是:「使用专线 ≠ 合法合规 ≠ 已报备。」

理由:

  • 线路合法不等于使用方式合法。专线是合法产品,但机场把企业专线转售给个人用于跨境访问,这个转售和使用环节本身就违反了「不转租、不提供公网接入」的承诺
  • 你作为终端用户,用的是被转租出来的企业专线,且用途(跨境访问)不属于「企业内网办公」
  • 「报备」是运营商对企业客户做的实名审批,跟你个人无关 —— 不会因为你用了这条线路就获得合法身份
  • 机场宣传的「IEPL 专线、稳定不掉线」讲的是技术质量,不是合规身份。这两件事经常被故意混在一起说
法律依据与风险分布(客观陈述)
  • 相关法规:《网络安全法》《数据安全法》《国际通信设施管理规定》;工信部多次发文清理「未经许可的 VPN、SD-WAN 等跨境连接服务」
  • 非法经营罪的追诉标准涉及「租用国际专线、私设转接设备,擅自经营国际电信业务或者涉港澳台电信业务进行营利活动」,并有明确的数额门槛(如经营去话业务数额 100 万元以上等情形)
  • 也就是说:「经营者」(机场)的风险远大于「使用者」;但使用者仍可能面临行政处罚

一句话总结:IEPL 是合法的基础电信产品,但把企业专线转售给个人用于跨境访问是违规的。专线的「合法」属于运营商与企业客户之间的关系,不传导到你身上。

本节只做事实陈述

上面讲的是「这件事在法律上处于什么位置」,不构成任何操作建议,也不涉及规避方式。

B6 · 链路解构:你 → 广州 → 专线 → 香港 → 目标

把这句行业黑话拆成可验证的一段一段。

段路径走什么网特征
①你家 → 广州入口普通公网国内段,延迟低(十几 ms),但可能被 QoS / 干扰
②广州机房 ↔ 香港机房IEPL 专线(不过公网)稳定、低丢包。这段是「机场花钱买的服务」
③香港服务器 → 境外网站当地国际带宽香港出口访问全球

广州这台的角色:入口(Entry),不是出口

你的问题问得很准,但要拆开「能力」和「职责」两件事:

  • 能力上:广州这台是台正常的服务器,它能路由到的地方它都能到(包括境外)。不是「没有能力」
  • 职责上:在这条链路里,它的角色被配置成中转(Relay)。你客户端配置里的 server 填的是这个入口域名,你的加密流量先到广州,广州再交给香港。整条链路的跨境出口是香港。

所以更精确的表述不是「广州连接香港再跨境」,而是:

你 --(普通公网,已加密)--> 广州入口 --(IEPL 专线)--> 香港出口 --(当地网络)--> 目标站 段① 段② 段③ 这一段加密后,旁观者只看到「你在访问广州」 机场的专线 真正从香港出海

跨境这个动作发生在哪? 发生在 ③,也就是「香港 → 目标站」这一跳。广州只是把包接过去,香港才是真正「出海」的那台。这就是行业里说的「入口」与「落地」分离:

角色职责决定了什么
入口 Entry你连的那个点,负责稳定接收你的第一跳延迟、是否易被干扰
中转 Relay中间跳,负责跨境运输链路的稳定性与抗封锁能力
落地 Exit / Landing真正访问目标站的点目标网站看到的 IP 归属
这下把附录 A 那个疑问也补全了

A3 提到「节点名写香港,IP 却在广州移动」。现在有了完整解释:

那个 IP 是「入口」,不是「落地」。节点名标注的是「落地」。

你节点名里的 IEPL 就是在说「段②是专线」,hk01 是在说「落地在香港」,entry 这个词干脆就写在域名里 —— ...entry.xxxxx-1.xyz。三个信息完全自洽。

为什么不直连香港,要绕这一下

方案路径优 / 劣
直连香港你 → 香港✅ 少一跳,理论延迟最低
❌ 这段是普通国际公网:可能被 QoS 限速(尤其 UDP / 大流量)、丢包、IP 被针对性干扰。晚高峰尤其明显
广州中转你 → 广州 → 香港✅ 段①是国内段,延迟低且稳定
✅ 段②走专线,避开「公网国际段」这个最不稳定的环节
✅ 段①被干扰就换入口 IP(GTM 抗封)
❌ 多一跳,多几毫秒

结论:这不是「绕远」,而是用「国内段 + 专线段」替换掉「公网国际段」。你付出的几毫秒,换来的是稳定性和抗封锁能力。

其他常见链路形态(以后看订阅可以对号入座)

形态链路特征
直连你 → 境外机便宜、延迟低但不稳,易被干扰
单跳中转你 → 国内中转 → 境外落地最常见
多入口中转你 → 就近入口(GTM) → 专线 → 落地好机场的标志,你订阅里的 IEPL 就属这类

B7 · TCP 的风险,与检测 / 伪装的攻防全谱

先纠正一个前提:说「TCP 有风险」不准确。准确说法是——

问题的核心

TCP 本身没问题。问题是「你看起来像什么」。

DPI 不看你「用了什么协议」,它看你「长得像什么」。所以下面讲的都是特征(fingerprint)问题。

四个可识别的特征

① SNI 明文

TLS 握手第一步,客户端发 ClientHello,里面有 SNI(我要访问哪个域名)—— 这个字段在标准 TLS 1.2 / 1.3 里是明文。

为什么必须明文?因为在加密建立之前,服务器得知道该给你哪张证书(一台服务器可能托管几百个域名)。

后果:ISP 能看见你访问哪个域名,哪怕内容全程加密。解法是 ECH(Encrypted Client Hello),把 SNI 也加密 —— 但需要浏览器和网站双方支持,目前普及度不高。

② TLS 指纹不像浏览器(JA3 / JA4)

ClientHello 里有一堆参数:TLS 版本、支持的加密套件列表、扩展的类型和顺序、椭圆曲线……

不同软件(Chrome / Firefox / OpenSSL / 代理客户端)发出的组合各不相同且相对固定 —— 这就是 TLS 指纹。代理客户端如果用某个库的默认握手,指纹会明显不同于任何浏览器。

后果:DPI 一看就知道「这不是浏览器,是个代理库」——根本不需要解密。解法是 client-fingerprint,让代理模仿 Chrome / Firefox 的握手参数。

③ 主动探测(Active Probing)

光看不够,还可以「敲门」。做法:检测系统发现某个可疑 IP,就主动向它发一个连接,看它怎么回应:

被探测对象回应结果
真的 HTTPS 服务器正常 TLS 响应 + 一张合法证书判定为正常网站
裸的代理服务器异常响应 / 拒绝 / 暴露协议特征暴露

这一步是致命的,因为纯被动分析只能「猜」,主动探测能「确认」。这也是为什么「让代理服务器背后真的有一个网站」如此重要。

④ TLS-in-TLS 包长特征

当代理协议本身跑在 TLS 里,而它承载的流量也是 TLS(你去访问 HTTPS 网站)时,就出现「TLS 套 TLS」。

特征:外层 TLS 记录的大小会精确地等于内层 TLS 握手包的大小(加上少量固定开销)。正常 HTTPS 的记录大小是连续变化的,TLS-in-TLS 会出现异常规整的分布。

用包长分布 + 时序做统计(甚至机器学习),能识别出来。解法是 填充(padding)、分片、限制早期数据大小(max-early-data)。

检测手段全景(按层)

注:DPI 的特点是分析副本,原始包继续转发,所以对吞吐影响小、但实现成本高。它也是目前最有效的识别手段。

伪装手段全景(对应解决哪一层)

Reality 的原理(最能说明「攻防」的一个例子)

普通 TLS 代理的做法是自己造一张证书 —— 需要域名、需要配置,而且证书指纹可疑、颁发者可疑,主动探测一来很容易识破。

Reality 的做法是不自己签名,去「借」一个真实网站的握手:

① 客户端(已预置目标网站信息)发起 TLS 握手 一开始伪装成要访问 www.microsoft.com ② 代理服务器不自己回应 —— 它把这次握手 转发给真正的 microsoft.com ③ 真实站点回应,带出 真实证书 ④ 代理把真实证书原样转发回客户端 ⑤ 客户端一看:证书是 microsoft.com 的,合法有效 ✓

三个关键后果:

  • 代理服务器没有自己的证书 → 无法通过证书特征识别它
  • 主动探测打过来 → 探测者看到的也是 microsoft.com 的真实响应 → 看起来就是个正常网站
  • 只有持有正确「暗号」(预置密钥 / proxy 参数)的客户端,代理才会切换到真实服务
一句话总结 Reality

它让代理服务器在所有人眼里(除了你)都是一个真网站。这就是「借真实网站握手」的含义,也是它目前被视为抗识别最强方案的原因。

B8 · 路由器能看到什么:一张可见性矩阵

先给结论:路由器(以及 ISP、同一 Wi-Fi 下的任何人)能看到「你去了哪」,能看到「你传了多少、什么时候、什么节奏」,但正常情况看不到「你说了什么」。

可见性矩阵

场景目标 IP域名URL 路径Cookie / Token账号密码内容 / 视频

逐条拆解

1. 明文 HTTP —— 全部可见

URL、Header、Cookie、表单、Body 全是明文。这就是浏览器弹「不安全」警告的原因。现在主流网站都是 HTTPS,这种情况主要出现在内网系统、老旧网站、以及某些 App 的接口。

2. HTTPS —— 这是最常见的状态

  • 能看到:目标 IP、SNI 域名、包长 / 时序
  • 看不到:URL 路径、query 参数、Cookie、Token、表单、响应内容、视频画面
  • 所以「路由器能看到你访问了 bilibili.com」,但看不到「你看了哪个视频」(内容层面)。理论上可以通过包长 / 时序指纹去猜,但那需要专门的分析能力,家用路由器不做这件事

3. 视频资源 —— 看不到画面

能看到看不到
你在哪个平台(SNI)画面内容
你在「看视频」这件事(视频流特征明显:持续下行、包大而均匀)具体是哪一集、哪一帧
经过了多长时间、消耗了多少流量——

学术上有「网站指纹 / 视频指纹」的研究,能识别到一定粒度,但那需要专门能力。家用路由器不做,ISP 层也不做这种细粒度分析(成本太高)。

4. Cookie / Token / 账号密码 —— 会暴露的三种情况

正常 HTTPS 下看不到(都在加密载荷里)。会暴露的只有这三种:

情况说明
a. 网站是 HTTP明文传输,全部可见
b. 设备装了观察者的根证书企业 / 学校的 TLS 拦截(SSL Inspection):代理会解密 → 检查 → 再加密。对应用完全透明,但证书链里会露出公司 CA
c. 代理本身是恶意的 / 被中间人典型例子就是你订阅里那个 skip-cert-verify: true 的免费节点 —— 客户端不校验证书,中间人可以冒充服务器解密你的 TLS
这解释了附录 A10 的建议为什么重要

skip-cert-verify: true 的节点,应急查资料可以,不要用它登录任何账号。因为在这种节点上,「账号密码被中间人看到」从「理论上不可能」变成了「有可能」。

5. 走了代理之后,路由器上看到什么

代理类型路由器能看到路由器看不到
加密代理(SS / VMess + TLS)你连了一台服务器(IP:端口),以及一堆看起来加密 / 随机的流量。连 SNI 都没有(SNI 在内层,被外层 TLS 保护)你在这条连接里访问了什么。完全不可见
裸 SS / 明文协议同上,但在具备 DPI 能力的网络里可能被识别出特征内容仍然看不到

从路由器视角看,「你在用代理」这件事本身可能可见(因为连接的持久性、流量模式很反常),但「访问目标」不可见。

6. TUN 模式会影响这个吗

不会

TUN 只改你本机自己的路由表,不改你出网流量的样子。路由器看到的东西完全一样。

唯一的差别是:TUN 会补上原本「某些应用不走代理」的漏网流量,让你的「实际走代理比例」更接近 100%。它改的是你自己这一侧,不是网络那一侧。

把结论收成四句
  • 「路由器能看到我的访问记录吗?」→ 域名层面能看到(DNS / SNI),前提是你没用「加密 DNS + ECH + 代理」这套组合
  • 「能看到账号密码吗?」→ 正常 HTTPS 下不能
  • 「能看 cookie / token 吗?」→ 不能(同上)
  • 「能看视频资源吗?」→ 看不到画面,能看出「在哪个平台、在看视频」

再补一句最该记住的:用代理后路由器只能看到你连了代理服务器 —— 但代理服务商能看到你的真实目标。信任只是转移了,不是消失了。

从网络设备分类上看,手机热点就是「由手机系统实现的便携式共享网络网关」—— 它的角色与家用无线路由器同类,只是硬件能力、配置能力和运行目标不同。

差异点

维度家用路由器手机热点
上行方式宽带 / 光猫 / 以太网4G / 5G 蜂窝(部分可共享上级 Wi-Fi)
供电长期外接电源手机电池(发热、耗电)
覆盖与天线通常更强受手机体积限制
并发设备更多更少
稳定性适合长期运行长期开启会发热、被系统策略影响
有线 LAN 口通常有通常没有
高级配置丰富(端口映射、DMZ、QoS、DDNS)少(个别支持端口映射)
移动性弱强
公网 IP通常有(可申请)常见在运营商 CGNAT 之后

差异带来的实际后果(这才是重点)

① 双层 NAT

热点下的电脑 → 手机 NAT → 运营商 CGNAT → 因特网

两跳 NAT 的后果:

  • 外部无法主动访问热点下的设备(端口映射基本失效)
  • P2P、游戏联机、自建服务、远程桌面 → 大概率失败
  • 能做 NAT 穿透的应用(STUN / TURN)还行,不能的就废

② 运营商对你的可见性 = 家用 ISP 一样

热点不是匿名化手段

运营商能看到:你连了哪些 IP、哪些域名(明文 DNS / SNI)、流量大小。HTTPS 保护内容,保护不了元数据 —— 跟有线宽带是同一套逻辑。

换句话说:换到手机热点,你换的是「哪家 ISP 在看你」,不是「没人看你」。

③ 计费与限速

运营商常把「热点流量」单独计费 / 限速(即使套餐写着「无限」)。这是运营商的策略限制,不是技术限制 —— 所以会出现「手机自己上网很快,热点却慢」。

④ Wi-Fi 中继的复杂性

手机连着 Wi-Fi 再开热点,不同系统行为不同:有的继续用移动数据、有的共享上级 Wi-Fi、有的干脆不允许两者同时工作。以手机实际显示的上联方式和路由配置为准。

⑤ 延迟

蜂窝链路多几处排队和调度,延迟通常高于有线宽带。浏览无感,对视频会议 / 实时协作有影响。
